## v0.1 能用

目标是回答一个问题：系统、额度和网络三类状态，放在一个菜单栏面板里是否好用。

内容：代码画的临时猫、总览条、三个标签页、底部操作、系统采集、能耗诊断、联动图、4 个渠道的额度和花费、嵌入 TunCanary、清理入口。布局和选项先写死默认值。

用户验收时看的问题：

- 三类状态放在一个面板里，是否拥挤，是否需要来回切换。
- 猫的速度和形态是否一眼能看懂。
- 能耗诊断能不能发现 `BTLEServer` 那类失控进程。
- 额度数据最多滞后 30 分钟，是否可以接受。

验收通过后，用户退出独立运行的 TunCanary，关闭它的开机启动（D23）。

### 已记录的产品深化方向

以下方向继续保留。表内顺序是此前建议，尚未单独确定高、中、低优先级；不覆盖上表用户明确的优先级。重点是异常解释和事后回看，复用现有系统趋势、网络探测、额度历史和提醒规则。

| 建议顺序 | 方向 | 目标与范围 |
| --- | --- | --- |
| 1 | 数据可信度与恢复 | 2026-10-23 用户确认要做，暂不启动规划。现状：只有“连续 N 次失败提醒数据源失效”（通知默认关），以及额度卡片上的最后成功时间和暂停说明；其余数据源没有统一的最近成功时间和过期判断。涉及的数据源有系统采集、传感器、能耗、各额度渠道、花费、Codex 重置预告、网络检测、代理流量和清理记录。规划时先定统一展示的位置、覆盖哪些数据源、状态分类、各源的过期阈值和可提供的恢复操作。统一显示每个数据源的最近成功时间、是否过期、失败原因和下次重试时间，并提供针对性的恢复入口。区分数据未变化与采集失效。重置预告已有部分能力，后续扩展到其他数据源。 |
| 2 | 统一异常时间线 | 从提醒打开异常详情，查看开始时间、持续时长、相关指标变化和恢复时间。保留异常前后的短快照，便于回看卡顿或断网；同时发生只作为关联线索，不直接判为因果。规划时明确记录范围、保留期限和本地存储上限。 |
| 3 | 额度使用规划 | 根据近期消耗估算可用时长，以及到重置前的每日可用量。明确样本覆盖范围和预测不确定性，样本不足时避免给出看似精确的结论。现有节奏公式和提醒默认值保持不变，调整前另行确认。 |
| 4 | 提醒解释与试算 | 展示规则为何触发及对应样本。调整阈值前，用已有历史试算触发次数和持续时间，帮助选择提醒强度；历史不完整时说明试算覆盖范围。 |
| 5 | 扩展本地 Agent 排查 | 在现有系统能耗诊断入口上，增加选中的网络或额度异常材料。用户预览、确认范围后交给已有 Agent；明确敏感字段处理，不自动上传全部历史。内置 AI 模块仍按 D31 暂缓。 |

这些方向可组合为“数据可信度与恢复 + 统一异常时间线”的小版本：统一数据源状态，再让提醒打开异常详情。该组合保留为候选，排期结合上表已确认优先级确定。

### 补充验证与观察

这些是验证边界和待观察事项，不把已完成的客户端修复重新列为未实现。

- 实机深色外观已于 2026-10-23 由用户确认验证。
- 网络失败排序、服务端退避和失败恢复、负功耗转缺测由合成回归覆盖。本次实机未人为制造故障，尚无这些异常的新增实机证据。
- 负功耗在 2026-10-11 修复后未再出现（用户 2026-10-23 确认）。成因仍未知；再次出现时保留原始样本，再追查来源。
- 自身性能测量工具（`scripts/profile-self.sh`）在 2026-10-07 至 2026-10-25 修复前，把 `proc_pid_rusage` 的 CPU 刻度当成纳秒，没有乘 `mach_timebase_info`。Apple Silicon 上 timebase 是 125/3，live 和 matrix 的绝对 CPU 百分比因此偏小约 41.7 倍，读旧记录时需乘 125/3；compare 的相对比值不受影响。修复后与 `ps -o time=` 交叉核对，偏差在 5% 以内。
- 重置来源的核验时效仍受上游影响。新内容获取和本机调度落盘已验证，不能据此承诺上游及时更新或账号到账。
