# MeowMac 决策记录

本文记录 2026-09-29 用户与规划者逐条讨论后确认的决策。编号在讨论中确定，后续引用保持不变，所以不连续。

本文受保护：只有用户能改。执行者发现实现和本文冲突时，按 `AGENTS.md` 的规则跳过并记录。

## 定位与路线

**D1　自建应用。** MeowMac 是个人优先的开源项目，MIT 许可，按作者自己的需求开发，不接功能请求。

否决的方案：

- fork RunCat Neo：它运行在 App Sandbox 里，不能起子进程，也读不到系统网络状态。
- 以 MacTools 为宿主写插件：它的功能覆盖面广，但每项都做得比较浅；编译需要 Xcode；第三方插件只能由同一 Team ID 签名的宿主加载；插件 ABI 从 v2 变到 v7。
- 合并 Mole 的代码：Mole 是 GPL-3.0，而且它在 M5 上读不到 CPU 温度和风扇转速。

**D2　技术栈。** SwiftPM + Command Line Tools，不安装 Xcode。最低 macOS 14。默认 ad-hoc 签名，安装到 `~/Applications/MeowMac.app`。2026-10-07 补充：ad-hoc 签名的系统授权（文稿等）绑定代码哈希，代码一变就重新弹窗；本地开发可用自签名证书（`scripts/setup-local-signing.sh`），构建脚本检测到就优先使用，没有则退回 ad-hoc。证书只在本机，不进入仓库，不对外分发；对外发布预编译包时再单独决定是否使用 Developer ID。2026-09-30 补充：Command Line Tools 升级到带 macOS 26 SDK 的版本，以便使用液态玻璃（D33）。升级由用户执行。

**D3　仓库与标识。** 仓库在 `~/projects/eastcn/meowmac`，bundle id 为 `io.github.eastcn.meowmac`。先只建本地仓库，推送到 GitHub 的 `eastcn/meowmac` 需要用户单独授权。TunCanary 先移到 `~/projects/eastcn/tuncanary`，MeowMac 用 `.package(path: "../tuncanary")` 依赖它。

否决的方案：在 TunCanary 仓库里扩展；把 TunCanary 源码搬进本仓库；用 git URL 依赖 TunCanary（本地改动要先推送、打标签，才能在 MeowMac 里用上）。

**D4　语言与名称。** 界面、注释和文档用中文，提交信息的格式与 TunCanary 一致。应用不叫 RunCat，也不使用 RunCat 的图标和猫的形象。

## 数据源

**D5　网络。** 通过 SwiftPM 依赖 TunCanary 的库。v0.1 直接嵌入它的 `MonitorController` 和 `PopoverRootView`。2026-09-30 修改：网络页改由 MeowMac 自己画，读取 `AppModel` 的公开数据，不再嵌入 `PopoverRootView`，见 D35。TunCanary 保持公开，进入维护模式，今后作为网络检测引擎，新的网络检测能力写进 TunCanary。

**D6　额度。** 调用 CodexBarCLI，只用 DeepSeek、Codex、Claude 和 OpenCodeGo 这 4 个渠道。CodexBar.app 不再常驻。计费数据来自 `cost --breakdown --json`，只有 Claude 和 Codex 有。

2026-10-05 修改：默认仍是这 4 个渠道。用户可以在“额度源设置”里，从 CodexBarCLI 支持的渠道中添加或移除渠道。新增渠道用通用卡片：有 CodexBar 图标就用，没有就用首字母圆形占位；显示窗口、节奏、趋势和历史，参与额度提醒和通知（D13、D41）。花费仍只有 Claude 和 Codex，按会话补刷（D8）仍只管 Claude 和 Codex，其他渠道按 30 分钟周期和手动刷新。渠道清单是本机配置，不进猫包。写 CodexBar 配置的范围见 `AGENTS.md`。

**D7　额度历史。** MeowMac 自己定时采样，写成 JSONL，放在 `~/Library/Application Support/MeowMac/`，保留 90 天。v0.2 时一次性导入 CodexBar 已有的历史文件。

**D8　刷新策略。**

- 每 30 分钟刷新一次全部渠道，不区分是否活跃。
- 每 60 秒扫描一次本地会话记录的修改时间，休眠时暂停。Claude 取 `~/.claude/projects` 下含子目录的所有 jsonl；Codex 取 `~/.codex/sessions` 下按名称排序最新的 3 个日期目录里的 jsonl。最近 120 秒内有写入算 active。某个渠道从 active 变成 idle 后，5 分钟后补刷这个渠道一次。
- 2026-10-04 修改（原为每 60 秒调用一次 `sessions --json-v2`）：`sessions` 与 `usage --provider codex` 每次都会触发 `spctl` 评估 ChatGPT.app，造成 `syspolicyd` 约 2.5 秒的满核峰值，`sessions` 又没有按渠道过滤的参数。语义随之变化：active 从“会话存活”变成“最近 120 秒有写入”，所以一次超过约 7 分钟的停顿也会触发一次补刷。
- 渠道的根目录不存在，视为未安装，按 idle 处理，不调用 CLI。根目录存在但读不了，或结构不符合预期，该渠道退回每 5 分钟调用一次 `sessions --json-v2`，并写一条不含路径的日志。120 秒和 300 秒是代码常量，补刷延迟仍由 `sessionFinishDelaySeconds` 决定。
- 支持手动刷新。距上次刷新不到 1 分钟的请求合并成一次。
- 打开面板只显示缓存和数据时间，不触发刷新。
- 休眠时暂停；唤醒后如果距上次刷新超过 30 分钟，立即补刷一次。

**D9　系统采集。** v0.1 只用公开接口：CPU、内存压力、swap、磁盘、网络、整机功耗、电池温度和 `thermalState`。精确的 SoC 温度和风扇转速要走私有接口，放到 v0.3 的实验卡片，读不到时显示“不可用”。

**D10　清理。** 面板显示磁盘空间和 `mo history --json` 的清理记录。点清理后打开终端运行 `mo clean`，由用户在终端里预览和确认。应用不在后台清理。

## 猫与健康

**D11　速度只表示负载。** 负载取 CPU 使用率和内存压力换算值中较大的一个，映射到每帧 0.5 秒（空闲）到 0.05 秒（满载）。内存用压力，不用已用百分比，因为 macOS 总会把内存用满。

**D12　健康状态用形态表示，分三档。**

| 档位 | 形态 |
| --- | --- |
| 正常 | 奔跑，速度随负载变化 |
| 提醒 | 照常奔跑，整只猫变成橙色（2026-09-30 确定） |
| 严重 | 停下来，不再按负载调速 |

同一时间只显示最严重的一档。v0.1 用代码画的剪影，三档靠颜色区分；正式美术放到 v0.2。

**D13　信号归档。**

- 严重：DNS 泄漏或 TUN 失效、站点探测连续失败、出口 IP 所在地区超出允许范围。
- 提醒：任一额度窗口剩余低于 20%、磁盘剩余低于 10%、`thermalState` 达到 serious 或以上、数据源失效、D14 的能耗异常。2026-09-30 补充：任一额度窗口按当前速度会在重置前用完，也算提醒，计算方法见 `docs/design/SPEC.md` 的「节奏的计算」。
- 2026-10-05 补充：余额型渠道（D6）的余额低于阈值也算提醒，按“额度不足”处理：可限时暂缓，归在通知的“额度不足”类别，正文写渠道、当前余额和阈值。阈值每个渠道单独设置，按该渠道的币种比较，默认 10，留空表示不提醒；在“设置 → 额度源”里修改，存本机配置，不进猫包。余额回到阈值及以上即恢复。余额没有重置周期，恢复后再出现按 D41 中“其他类”的规则通知。

**D14　能耗诊断。** 放在 v0.1 的系统页。温度只是症状，进程引起的能耗异常才是根源。

原因层：

- 进程能耗排行前 5 名。每 60 秒用 `top` 采样一次，显示进程名、CPU 和能耗影响分。
- 失控进程：单个进程占用超过一个核心的 90%，持续 10 分钟。
- 内存压力处于 warn 或以上，持续 10 分钟。

2026-10-01 修改：删去“休眠被阻止”（某个进程持有阻止休眠的断言超过 2 小时）。ChatGPT、Claude 这类正在干活的应用会正常阻止休眠，不代表能耗异常；真卡住的进程由失控进程规则发现。

症状层分两级：

- 建议降温：`thermalState` 为 fair 并持续 5 分钟。v0.3 起，风扇转速超过最大值的 80% 并持续 5 分钟也算。只在总览条上加一个标记，猫的形态不变。
- 已降频：`thermalState` 达到 serious 或以上，归入提醒档。

判定只看 CPU。能耗影响分是 Apple 的启发式分数，没有单位，只用来排序和展示。

发现异常时只提示“建议用 AI 诊断”。只有温度偏高、没找到异常进程时，提示“温度偏高，未发现异常进程，建议降温或用 AI 诊断”。不提供结束进程的按钮。

2026-10-06 修改（用户授权）：“建议用 AI 诊断”的提示旁可以提供入口，唤起本机已安装的 agent 排查，不再限定为纯文字提示。约束：

- 只在用户点击入口时唤起，不自动唤起。
- 只唤起本机 agent，MeowMac 自己不调用任何外部 AI 服务，D31 不变。
- agent 只负责排查和给出建议。结束进程仍由用户自己操作，MeowMac 不代劳，也不让入口带上“结束进程”的指令。
- 带给 agent 的上下文包含哪些字段、支持哪些 agent、如何唤起，开始实现前由用户确认。

例子：`BTLEServer` 卡在忙循环里，持续占满一个核心。整机 CPU 只高了几个百分点，只看猫的速度发现不了；失控进程规则能直接指出它。

**D14a　技术验证。** v0.1 验证 `proc_pid_rusage` 的 `ri_energy_nj` 能否读到其他用户和 root 的进程。结果只记录，由规划者决定是否用它替代 `top` 子进程。

**D15　判定规则的位置。** 健康判定规则写在统一的本机配置里，不随猫配置切换。

## 面板与配置

**D16　面板结构。** 顶部是总览条，中间是系统、额度和网络三个标签页，底部固定放刷新、清理和设置。容器用弹出面板，不用 `NSMenu`，因为 `NSMenu` 一点击就关闭，放不了多步交互。

**D17　默认标签页。** 打开面板时显示问题最严重的那一类。都正常时显示上次看的那一页。

**D18　总览条。**

- 第 1 行：当前档位、最严重的问题、降温标记。点击问题跳到对应标签页。一切正常时显示“一切正常”和最近刷新时间。
- 第 2 行：CPU、内存压力、一个可选的额度窗口、网络状态灯。额度窗口默认是 Claude 的 5 小时窗口，默认显示剩余，也可以改成已用。2026-09-30 修改：4 块都显示数字。内存显示已用百分比和已用/总量，压力只用横线颜色表示（2026-10-01 修改：内存改为显示压力百分比，即 100 减去 `kern.memorystatus_level`，横线长度和颜色都跟着压力；下面一行写已用/总量，已用按活动监视器的口径，等于 App 内存、联动内存和被压缩之和。原口径把文件缓存也算进已用，常年接近 100%）；网络显示实时下行和上行速率，结论只用横线颜色表示。细则见 `docs/design/SPEC.md`。

**D19　布局以卡片为单位。** 卡片用代码实现，遵守同一个 `Card` 协议。标签页只是卡片的分组，由配置文件决定。卡片内部显示什么，由卡片自己的设置决定。

**D20　猫配置。** 一只猫是一个目录，例如 `年糕.cat/`，包含菜单栏帧图、面板样式、布局、总览条和卡片显示选项。不包含健康判定规则、刷新策略、数据源配置和凭据，所以可以放进 git，也可以分享。同一时间只有一只猫生效。

**D21　可插拔接口。** 额度源和采集项通过统一接口接入。机场订阅额度会用到它。

**D30　联动图。** 系统页常驻一张联动图：CPU 负载、整机功耗和电池温度共用一条时间轴，背景用 `thermalState` 着色。时间范围可选 15 分钟或 1 小时。用途是观察高负载时功耗和温度怎么变化，不依赖异常触发。v0.3 再加上 SoC 温度和风扇转速。

## 设计（2026-09-30 确定）

v0.1 第一轮交付的界面不合格，原因是规划里没有视觉要求。这一节补上。

**D32　设计稿是实现依据。** 设计稿源文件在 `docs/design/mockups/`，规范在 `docs/design/SPEC.md`。界面实现以这两份为准，和设计稿不一致的地方视为缺陷。2026-09-30 已按 D39 更新为终稿版本。风格参照 CodexBar：分节平铺，细进度条，次要信息靠右，用灰色。

**D33　液态玻璃。** 用 macOS 26 SDK 编译，使用系统的液态玻璃材质；macOS 14～15 退回普通材质。代码用 `#available(macOS 26, *)` 区分。否决的方案：保持 SDK 14.4，用 `NSVisualEffectView` 模拟，因为效果和系统里的其他软件不一致。

**D34　额度页的内容。** 在窗口和花费之外，增加账号和套餐、节奏预估（进度条上的刻度和文字）、可重置次数、用量趋势（长周期折线，5 小时窗口画成每个窗口的峰值柱状图）和本地存储。本地存储只显示大小和“在访达中显示”，不提供删除，理由同 D10。

**D35　网络页自己画。** 读取 TunCanary `AppModel` 的公开数据，用 MeowMac 的视觉重新呈现，不修改 TunCanary。

**D36　菜单栏猫。** v0.1 用设计稿里的矢量版；v0.2 做猫配置时再细致打磨，或者换成 AI 绘制的素材。负载不低于 0.7 时加三道速度线。

**D37　渠道 logo。** 用 CodexBar 仓库里的 `ProviderIcon-*.svg`。logo 是各公司的商标，公开发布时在 README 里注明。

**D38　设置入口。** 底部“设置”按钮弹出菜单，v0.1 不做设置窗口，阈值等配置通过“打开配置文件…”修改。

2026-10-05 修改：改为统一的“设置…”窗口（⌘,），左侧边栏分通用、外观、猫、网络、额度源、通知六栏，取代各自独立的设置窗口和设置菜单里的子菜单。开关和单选点了即生效；外观、网络、额度源保留“取消/保存”，有未保存的修改时切换栏目或关闭窗口要先确认。底部“设置”按钮仍弹出精简菜单：设置…、打开配置文件…、在访达中显示配置目录、关于、退出。阈值等不在界面里的配置仍通过“打开配置文件…”修改。

**D39　先对比设计稿，再单独实现。** 用同一份设计需求（`docs/design/BRIEF.md`）让 GPT 另出一版视觉稿，和现有画布对比，挑一版或取两边的长处合成终稿，再交给一个执行者实现。现有画布和 `SPEC.md` 在终稿确定前只是候选方案之一。否决的方案（同日早些时候的 D39）：同一份 plan 由 GPT 和 Opus 各实现一版再比较，因为实现成本翻倍，而分歧主要出在设计上，应该在设计阶段解决。

2026-09-30 结果：两版合成终稿。版式取 GPT 稿：总览指标平铺、数字 20pt，图表占满整行，排行、站点和出口 IP 用表格，花费用两个大号金额（2026-10-01 修改：改为今天、近 7 天、近 30 天三个）。规则取原画布：横线颜色只表示状态（2026-10-01 修改：额度页的横线和图表改用渠道色，状态由文字颜色表示；总览仍用状态色），节奏刻度是红线，5 小时峰值柱超过 80% 变橙（2026-10-01 修改：改为渠道色实色，其余柱半透明），趋势图有匀速用完的虚线，能耗诊断是可以列多条的列表，设置用原生 `NSMenu`，菜单栏猫沿用原画布。GPT 稿保留在 `docs/design/gpt/`，只作参考，实现以 `mockups/` 和 `SPEC.md` 为准。

**D40　提醒查看与限时暂缓（2026-10-02）。** 本项补充 D12、D13、D17、D18 和 D32。检测规则和阈值沿用原决策，提醒管理按下列规则执行。

- 总览增加“全部提醒”入口。提醒列表在同一弹出面板中打开，按系统、额度和网络筛选，区分待关注与已知晓。降温提示单列，不参与猫的健康档位。
- 额度不足、额度偏快、磁盘不足和数据源失效允许限时暂缓。按钮文案为“我已知道…”，点击后选择时长，确认保存后才生效。支持 30 分钟、1 小时、4 小时、1 天、2 天、3 天和自定义时长。自定义使用整数分钟、小时或天，范围为 1 分钟至 30 天。额度有可靠的未来重置时间时，可选“直到本轮重置”。
- 暂缓项保留在已知晓列表，不参与总览告警档位或猫的健康形态判定。其他未暂缓问题继续参与判定。各页的实际风险色、原始数值和数据失效说明仍保留。猫的速度仍只表示负载。
- 网络严重故障、网络黄色提醒、持续高 CPU、持续内存压力和系统热状态严重不支持暂缓。检测确认恢复后消除。建议降温保持原有标记，不支持暂缓。
- 暂缓保存绝对到期时间，不随猫配置切换。关闭面板、重启和休眠不延长时长。到期仍有问题时重新提醒。检测恢复后重现、额度进入新重置周期或问题升级为严重时，旧暂缓不沿用。采集失败、未知或未完成检测不代表恢复。
- 打开面板时，按最严重的待关注问题选择标签页。没有待关注问题时显示上次看的页。仍有已知晓问题时，总览写“当前无待关注提醒”，并显示已知晓项数；全部检测恢复后才写“一切正常”。
- 首版只列当前问题，不保存已恢复历史，不提供永久忽略、批量暂缓或删除历史。不新增 macOS 系统通知，不改变 TunCanary 已有的通知行为（2026-10-05 修改：由 D41 取代）。
- 提醒管理是本机配置，不写入可分享的猫包。保存失败不虚报暂缓成功；坏文件保留，回退为没有暂缓，并显示恢复说明。
- 交互与设计依据补充 `docs/design/mockups/alerts.html` 和 `docs/plans/2026-10-02-alerts/design.md`。对话中的合成演示用于确认交互，不能代替原生容器、材质与用户实机验收。

**D41　MeowMac 统一发系统通知（2026-10-05）。** 本项修改 D23 和 D40 中关于通知的规定，其余不变。

- 提醒被确认出现时，由 MeowMac 发一条 macOS 系统通知。范围是网络故障、出口 IP 变化、额度不足、额度偏快、磁盘不足、进程 CPU 持续偏高、内存压力持续偏高、系统已降频和数据源失效。降温提示只保留标记，不通知。
- TunCanary 不再直接发通知。MeowMac 给它注入自己的通知实现：故障通知丢弃，改由 MeowMac 按自己的提醒生成；出口 IP 变化转成 MeowMac 的通知；地域恢复不通知。不修改 TunCanary。
- 通知内容要具体：写明对象、当前数值，以及重置时间、预计用完时间或已持续的时长。
- 同一个问题持续期间只通知一次。额度类同一个重置周期内最多通知一次。严重档在确认恢复满 10 分钟后再次出现，就再通知一次；其他类要恢复满 1 小时后再出现才通知。从提醒升级为严重时立即通知。已暂缓的问题不通知；暂缓到期后问题仍在，通知一次。
- 点通知打开面板，并跳到对应的标签页。不提供通知里的操作按钮。
- 开关在设置菜单的“系统通知”子菜单里，包括总开关和各类开关。默认全开，数据源失效默认关。开关是本机设置，不进猫包，也不提供配置文件编辑入口。

**D42　提醒规则（2026-10-07）。** 本项修改 D13、D14、D38 和 D41 中关于检测阈值、内存提醒和通知开关的规定，其余不变。

- 提醒检测改为规则。一条规则包含一个指标、比较方式（≥ 或 ≤）、阈值、持续时长和档位（提醒或严重），外加启用和发通知两个开关。规则清单和指标目录见 `docs/plans/2026-10-07-alert-rules/design.md`。
- 内置规则沿用 D13、D14 的检测和默认阈值，内存规则除外。用户可以在设置里调整内置规则允许调整的阈值和持续时长，也可以停用整条规则。停用的规则不检测、不通知、不影响猫的形态；各页的原始数值和风险色照常显示。网络规则来自 TunCanary 的判定，只能开关，不能调阈值。
- 内存提醒改为“内存压力百分比达到阈值并持续 10 分钟”，百分比与面板显示的压力% 同一口径（100 减 `kern.memorystatus_level`）。默认阈值由实机校准确定，写入设计文档。猫的速度仍按 D11 用内核档位换算。
- 用户可以从指标目录中选一个指标新建规则，最多 32 条。指标只来自已有采集，不引入新数据源，不执行用户提供的命令或脚本。自定义规则与内置规则同等对待：进入“全部提醒”，影响猫的形态，可发系统通知，并遵守 D40 的暂缓规则（提醒档可限时暂缓，严重档不可）和 D41 的去重与冷却规则。
- 设置窗口的“通知”栏改名为“提醒”，集中列出全部规则及其当前状态。阈值、持续时长和自定义规则可以在界面里修改，D38 中“阈值通过配置文件修改”的规定对提醒规则不再适用。规则定义存在 `config.json`（D15），仍可通过“打开配置文件…”修改。
- 系统通知的开关由 D41 的固定类别改为每条规则一个开关，加一个总开关。默认值沿用 D41：除数据源失效外全部开启；自定义规则默认开启。开关仍是本机设置，不进猫包，不提供配置文件编辑入口。旧的类别开关按设计文档的映射自动迁移。
- 规则和通知开关都是本机配置，不写入可分享的猫包（D20）。

**D43　代理流量统计（2026-10-13）。** 本项是 D5 的例外，其余不变。

- 本机经代理流量的统计由 MeowMac 自己实现，不写进 TunCanary，也不修改 TunCanary。只调用 TunCanary 已公开的 `MihomoController.locate()` 取得控制 socket 路径；读取 `/connections` 的客户端由 MeowMac 自己实现，只读，不调用任何写接口。
- 数据格式遵循 meowkit 仓库的 `mihomo-traffic/SCHEMA.md`（`mihomo-traffic/v1`），来源名 `mac`，不记录来源 IP。
- 每 5 秒采样一次，结果只在内存中累计；每 5 分钟写一次本地检查点；按小时汇总，写入 `~/Library/Application Support/MeowMac/history/proxy-traffic/`，保留 30 天。
- 可选导出：`config.json` 的 `proxyTrafficExportDirectory` 不为空时，每个小时结束后把这一小时的汇总行追加到该目录下的 `mac/YYYY-MM-DD.jsonl`。只追加，不重命名，不建临时文件；删除该子目录下超过 30 天、文件名符合 `YYYY-MM-DD.jsonl` 的文件。默认为空，不导出。
- 网络页新增“代理流量”功能块 `network.proxy`，设计稿见 `docs/plans/2026-10-13-proxy-traffic/design.html`。

**D44　电池与续航（2026-10-24）。** 本项补充 D9 和 D30，其余不变。

- 电池读数来自 IORegistry 的 `AppleSmartBattery`（与 D9 的电池温度同源，不需要 sudo），按字段白名单读取：电量、供电与充放电状态、电压和电流、系统给出的平均预计时间、最大容量、循环次数和适配器额定功率。不读取、不记录序列号；不使用公开接口里的电池健康文字。
- 预计时间只显示系统给出的值，MeowMac 不自行推算续航。
- 每 5 分钟记录一个电量点，供电状态变化时立即补记一点，写入 `~/Library/Application Support/MeowMac/history/battery/`，保留 24 小时。
- 系统页新增“电池”功能块 `system.battery`，默认排在磁盘之后；没有电池的 Mac 不显示。设计稿见 `docs/design/mockups/battery.html`。

**D45　桌面猫（2026-10-25）。** 本项补充 D11、D12、D20、D33 和 D38，其余不变。

**D46　桌面猫显示 AI 会话（2026-10-25）。** 本项补充 D8、D31 和 D45，其余不变。

## 附录：已验证的事实

以下事实在 2026-09-29 于作者的 MacBook Pro（Apple M5，16 GB，macOS 26.6.2）上验证。

**CodexBarCLI 0.60.5**（2026-10-04 实测已是 0.70.0），路径 `/Applications/CodexBar.app/Contents/Helpers/CodexBarCLI`。

- CodexBar.app 退出后仍能正常工作。
- `usage --provider <p> --json` 的耗时：Claude 12～14 秒，Codex 4～6 秒，DeepSeek 1 秒，OpenCodeGo 1～2 秒。每次都实时请求，不读缓存。
- 返回一个数组，每项有 `provider`、`source` 和 `usage`。`usage` 里有 `primary`、`secondary`、`tertiary` 三个窗口，每个窗口有 `usedPercent`、`windowMinutes`、`resetsAt` 和 `resetDescription`，字段可能缺失。有的渠道还有 `pace`，含 `summary`、`willLastToReset` 等字段。Codex 另有 `credits` 和 `usage.providerCost`。
- `dashboard` 一次返回所有已启用的渠道，单个渠道失败会作为这一行的错误返回；支持 `--timeout` 和 `--output`。耗时未测。
- `cost --provider <claude|codex> --days N --breakdown --json` 读本地日志，耗时不到 1 秒。返回 `daily[]`，每项有 `date`、各类 token 数、`totalCost` 和 `modelBreakdowns`。Codex 另有 `projects[]`。
- `sessions --json-v2` 耗时约 1 秒（2026-10-04 实测约 2.5 秒，其间会启动 `spctl --assess` 评估 ChatGPT.app；`usage --provider codex` 同样会，`cost` 不会）。每个会话有 `provider`、`state`（`active` 或 `idle`）、`lastActivityAt`、`startedAt`、`pid` 等字段。只覆盖 Claude Code、Codex、pi 和 OMP。
- CodexBar.app 的额度历史在 `~/Library/Application Support/com.steipete.codexbar/history/<provider>.json`，由应用写入，CLI 不能导出。

**系统数据。**

- `top -l 2 -s 1 -o power -stats pid,command,cpu,power` 不需要 sudo，能列出所有用户的进程，包括 `WindowServer`。第二次采样的 %CPU 是 `-s` 指定的这段时间的平均值；能耗判定用 `-s 60`，窗口等于采样间隔，首尾相接（2026-10-04）。进程名最多显示 16 个字符。
- IORegistry 的 `AppleSmartBattery` 不需要 sudo 就能读：`Temperature` 是百分之一摄氏度（3051 表示 30.51°C）；`PowerTelemetryData` 里有 `SystemLoad` 等功耗字段，单位待核对。
- SDK 头文件里 `rusage_info_v6` 有 `ri_energy_nj` 字段。
- `mo status --json` 在 M5 上的 `cpu_temp` 和 `fan_speed` 都是 0。
- `mo clean` 是交互式终端程序，没有 JSON 输出。需要 sudo 时会停下来等按键。

**TunCanary。**

- `MonitorController` 和 `AppModel` 是 `public` 的。界面层只公开了整个弹窗 `PopoverRootView`，7 个卡片视图是 `internal`。
- `AppModel` 的 `overall`、`local`、`siteHistory`、`egressResults`、`egressState`、`lastCheckedAt` 是 `public` 的（2026-09-30 核实）。这些类型内部的字段能否在 TunCanary 外面读到，实现时再逐个核对。
- `SettingsStore()` 在当前 bundle id 不是 TunCanary 时，使用 `UserDefaults(suiteName: "io.github.eastcn.tuncanary")`，所以嵌入后读到的是用户现有的 TunCanary 设置。
